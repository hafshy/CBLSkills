# CBL Applied to Building a Product

## Where "Product Development" Sits in the Framework

The official CBL framework names **product development** explicitly as one type of valid Solution Concept in the Act phase, alongside campaigns, school/community improvement projects, and other interventions. This means CBL's Act phase already maps closely onto a standard product-build cycle:

1. **Solution Concepts** → ideation / concept selection
2. **Solution Development** → prototyping, experimentation, testing (iterative design cycle)
3. **Implementation and Evaluation** → shipping to real users, measuring outcomes, reflecting, iterating or closing out

## How the Full CBL Arc Maps to Product Building

| CBL Phase | Product-Building Equivalent |
|---|---|
| Engage (Big Idea → Essential Question → Challenge) | Problem framing / opportunity identification — defining *why this matters* and *what specific problem* you're solving |
| Investigate (Guiding Questions → research → synthesis) | User research, market/competitive research, technical feasibility research, requirements gathering |
| Act: Solution Concepts | Ideation, concept sketches, choosing a direction (akin to a product brief) |
| Act: Solution Development | Prototyping, building, iterating — the engineering design process (define → brainstorm → build → test → improve) |
| Act: Implementation & Evaluation | Launch/release to real users, collect usage/outcome data, retro |
| Reflect/Document/Share (continuous) | Product documentation, changelog, case study, demo/pitch |

## The Engineering Design Process Connection

CBL's Solution Development step is explicitly compatible with the standard **Engineering Design Process (EDP)**: a structured, repeatable method guiding students through defining problems, brainstorming solutions, building prototypes, testing ideas, and improving designs through iteration. This is the same loop used in most product/design-thinking methodologies (e.g., design thinking's Empathize–Define–Ideate–Prototype–Test).

Key point: the CBL guide is explicit that this is an **iterative design cycle** — prototyping and testing regularly surface new Guiding Questions that send the team back into Investigate. A skill for product building should treat this back-and-forth as expected, not a detour.

## Practical Sequence for a Student Product Team

1. **Frame the problem** (Engage): pick a Big Idea relevant to the team, distill an Essential Question, write one Challenge statement describing the problem to solve — framed as an action, not just a topic.
2. **Research before building** (Investigate): don't jump straight to building. Generate Guiding Questions about users, the problem space, existing solutions, and technical constraints; research and synthesize before locking a direction.
3. **Concept and scope** (Act — Solution Concepts): generate a few product directions, evaluate against the Investigate findings, pick one and get it validated by a mentor/stakeholder/teacher.
4. **Prototype and test** (Act — Solution Development): build a minimal version, test it with real or representative users, expect to loop back to Investigate as new questions surface, refine.
5. **Ship and measure** (Act — Implementation & Evaluation): release to an authentic audience (not just present to the class), define success metrics up front, measure real outcomes, reflect honestly on what worked/didn't.
6. **Share** (continuous thread): publish documentation, a demo, or a case study of the product and the process — sharing publicly is treated as part of the learning, not an optional extra.

## Design Guidance for the Claude Skill

Because CBL's Act phase is explicitly iterative and non-linear, a "build a product" skill should:
- Never treat Investigate as a one-time, closed step — allow/encourage the student to return to research when prototyping surfaces unknowns.
- Push for a *real* audience/test at the Implementation step, not just a simulated demo — authenticity is a CBL principle, not a nice-to-have.
- Bake in a lightweight "define success metrics before you build" step, since CBL calls for measuring outcomes against the original Challenge.
- Prompt for a completion artifact (report, case study, or demo) as a natural closing deliverable, tying back to the "Reflect, Document, Share" thread.
